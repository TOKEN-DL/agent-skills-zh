# Definition of Done

一份跨项目的常驻门槛，任何改动要算做完都得先过这道坎。它与"接受标准"（per-task，回答"我们做对了么？"）不同；Definition of Done 每次都一致，回答的是"它达到我们的标准了么？"。在 `planning-and-task-breakdown`、`incremental-implementation`、`shipping-and-launch` 的最后一关用它。

## Definition of Done vs. 接受标准

| | 接受标准 | Definition of Done |
|---|---|---|
| 范围 | 特定任务的规格 | 适用于每个增量 |
| 是否变 | 每条都不同 | 固定且复用 |
| 回答 | "我们做了*这个*了么？" | "它*准备好*了吗？" |
| 由谁定 | 任务规划时定义 | 整个项目一次性定 |
| 例子 | "用户能通过邮件链接重置密码" | "测试通过、无回归、文档已更新" |

两份互补。一个任务只在**它的**接受标准达成**并且**常驻 Definition of Done 也满足时才算做完。跳过任何一边，留下的活看起来完成、实际没有。

## 常驻清单

宣告完成之前，对每一项改动都过一遍这份清单。

### 正确性
- [ ] 任务全部接受标准达成
- [ ] 代码能跑、行为如预期，已经在运行时验证、不仅是编译或类型检查过
- [ ] 新行为有测试覆盖，测试在没有改动时挂、有改动时过
- [ ] 已有测试仍通过；没有引入回归
- [ ] 边界情况与错误路径都处理了，不只是快乐路径

### 质量
- [ ] 代码通过命名与结构自证意图；不需要注释解释 *what*
- [ ] 没有重复的业务逻辑
- [ ] 没有遗留的死代码、调试输出、注释掉的块
- [ ] 改动严格限定在任务范围；没有不相关的重构悄悄混进来
- [ ] Lint 与格式化通过

这些项背后的深度说明在 `code-review-and-quality`（五维度评审）与 `code-simplification`（保留行为前提下的复杂度削减）里。

### 集成
- [ ] 改动能跟系统其它部分一起工作，不只是孤立场景
- [ ] 数据库迁移、配置变更、特性开关都被考虑到
- [ ] 任何公开接口或 API 改动都考虑了向后兼容

### 文档
- [ ] 公开接口、API、用户可见行为有文档
- [ ] 值得保留的架构决策已被记录（见 `documentation-and-adrs`）
- [ ] 文档用"现状"的语言描述当前状态、不是变更史

### 上线准备度
- [ ] 任何不可信输入、认证、数据处理都复盘过安全影响（见 `security-and-hardening`）
- [ ] 关键新路径已埋好可观测性（日志、指标、追踪）（见 `observability-and-instrumentation`）
- [ ] 任何有风险的改动都有回滚路径（见 `shipping-and-launch`）
- [ ] 在合并或部署前有人类评审并批准

## 怎么用

- **每次任务：** 在把任务勾掉之前，先核 Correctness 与 Quality 两节。
- **每个特性：** 在说特性完成之前，核 Integration 与 Documentation。
- **每个发布：** 完整清单是底线；`shipping-and-launch` 在上面再加部署相关的闸。

按项目把清单一次性裁好、之后不动。一个每个迭代都被重新谈判的 Definition of Done 不是 Definition of Done。

## 红旗

- "做完了，只是还没跑"：未验证的活不算做完。
- 把 "测试通过" 当 "完成" 的同义词，跳过文档、回归或运行时验证。
- 同一份清单按截止日期的压力换不同的标尺。
- 把接受标准当成全部门槛、没有常驻质量底线。
- 需要人类评审的改动，在评审前就宣告"完成"。
