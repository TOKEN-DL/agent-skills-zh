# Incremental Implementation

## 概述

做薄垂直切片 ， 实现一片、测一片、验证一片、再扩。避免一次性把整个功能写完。每个增量应该让系统处于可工作、可测试的状态。这是把大型特性变得可控的执行纪律。

## 何时使用

- 实现任何跨多文件的改动
- 按任务拆分构建新特性
- 重构既有代码
- 任何你想在测试前一口气写超过 ~100 行的时候

**不用：** 单文件、单函数的改动，范围已经很小。

## 增量循环

```
┌──────────────────────────────────────┐
│                                      │
│   实现 ──→ 测试 ──→ 验证 ──┐          │
│       ▲                    │          │
│       └──── 提交 ◄──────────┘          │
│             │                         │
│             ▼                         │
│        下一片                          │
│                                      │
└──────────────────────────────────────┘
```

对每一片：

1. **实现**完整可工作的最小功能块
2. **测试** ， 跑测试套件（或在没有测试时先写一条）
3. **验证** ， 确认切片按预期工作（测试通过、构建成功、手工检查）
4. **提交** ， 用一条描述性的提交信息保存进度（参见 `git-workflow-and-versioning` 关于原子提交）
5. **下一片** ， 接力下去，不要重启

## 切片策略

### 纵向切片（首选）

每次构建一条贯穿全栈的完整路径：

```
切片 1：创建任务（DB + API + 基础 UI）
    → 测试通过，用户通过 UI 能创建任务

切片 2：列出任务（查询 + API + UI）
    → 测试通过，用户能看到自己的任务

切片 3：编辑任务（更新 + API + UI）
    → 测试通过，用户能改任务

切片 4：删除任务（删除 + API + UI + 确认）
    → 测试通过，CRUD 完成
```

每片都交付可工作的端到端功能。

### 契约先行的切片

当后端和前端要并行开发：

```
切片 0：定义 API 契约（类型、接口、OpenAPI spec）
切片 1a：按契约实现后端 + API 测试
切片 1b：按契约实现前端，Mock 数据匹配契约
切片 2：联调端到端
```

### 风险先行的切片

先啃最不确定 / 风险最大的部分：

```
切片 1：证明 WebSocket 连接能用（最高风险）
切片 2：在已验证连接之上构建实时任务更新
切片 3：加离线支持与重连
```

如果切片 1 失败，你在为切片 2、3 投入之前就发现了。

## 实现规则

### 规则 0：先求最简

动笔前先问："什么是最简单又能 work 的事？"

写完后，对照这些自查：
- 能用更少的行做完吗？
- 这些抽象挣回了它们带来的复杂度吗？
- 资深工程师看到这个会不会说 "为什么你不直接……"？
- 我在为假想的未来需求建，还是只为眼前任务？

```
最简化自检：
✗ 为一个通知造一个带中间件管线的通用 EventBus
✓ 一个简单函数调用

✗ 为两个相似组件用抽象工厂模式
✓ 两个直白组件+共享工具函数

✗ 为三个表单用配置驱动的表单构造器
✓ 三个表单组件
```

三行类似代码好过过早抽象。先实现"显然正确"的朴素版。在用测试证明正确性之后再优化。

### 规则 0.5：范围纪律

只动任务要求的部分。

不要：
- "清理" 跟你改动相邻的代码
- 重构你没在改的文件里的 import
- 删除你完全没看懂的注释
- 加规格之外的特性因为"似乎有用"
- 在你只在读的文件里"现代化"语法

如果注意到任务范围之外值得改的地方，记下来 ， 别动：

```
注意到但不动：
- src/utils/format.ts 有一个没用的 import（与本任务无关）
- auth middleware 错误消息可以更好（另开任务）
→ 要不要我给这些建任务？
```

### 规则 1：一次只做一件事

每个增量改一个逻辑上的事。不要混在不同关注点：

**坏：** 一条提交里加新组件、重构已有组件、改构建配置。

**好：** 三条独立提交 ， 每条改一个事。

### 规则 2：保持可编译

每个增量之后，项目必须能构建、已有测试必须通过。不要在切片之间留破损的代码库。

### 规则 3：用特性开关承载未完的特性

一个特性还没准备好给用户但你需要合入增量：

```typescript
// 进行中的特性开关
const ENABLE_TASK_SHARING = process.env.FEATURE_TASK_SHARING === 'true';

if (ENABLE_TASK_SHARING) {
  // 新版分享 UI
}
```

这样能让你把小的增量合入 main 又不暴露未完的工作。

### 规则 4：安全默认值

新代码应该默认走安全、保守的行为：

```typescript
// 安全：默认关闭，opt-in
export function createTask(data: TaskInput, options?: { notify?: boolean }) {
  const shouldNotify = options?.notify ?? false;
  // ...
}
```

### 规则 5：可回滚

每个增量应该可以独立 revert：

- 加性改动（新文件、新函数）易回滚
- 已有代码的修改应该最小且聚焦
- 数据库迁移要有对应回滚迁移
- 避免在一条提交里删一个东西又在同一提交里加替代 ， 拆开

## 与 Agent 协作

指导 Agent 做增量实现时：

```
"我们来做规划里的 Task 3。

先只做数据库 schema 变更和 API endpoint。
先不动 UI ， 那是下个增量的事。

实现之后，跑仓库自己的测试与构建命令验证
没破坏什么。"
```

对每个增量，明确说清楚什么在范围、什么不在。

## 增量清单

每个增量之后，按仓库自己的命令做验证（参见 test-driven-development Skill 的"先发现栈"小节）：

- [ ] 改动做了一件事且做完了
- [ ] 已有测试全部通过（仓库的测试命令：`npm test`、`./gradlew test`、`pytest`、...）
- [ ] 构建成功（仓库的构建命令）
- [ ] 类型检查通过，如果有的话（`npx tsc --noEmit`、`mypy`、...）
- [ ] Lint 通过（仓库的 lint 命令）
- [ ] 新功能按预期工作
- [ ] 改动用一条描述性的 message 提交了

**注意：** 仅在可能影响结果的改动后跑相应验证命令。一次成功跑过之后，不要再跑同一条命令除非代码有变 ， 在未改动的代码上重跑不增加信息。

## 常见借口

| Rationalization | Reality |
|---|---|
| "我等到最后再测" | Bug 会叠加。切片 1 里的 bug 让 2-5 都错。每片都测。 |
| "一把全做完更快" | 直到 break 之前 *感觉* 更快，但你从 500 改动的行里找不到是哪一行引发的。 |
| "这些改动太小，不必分开提" | 小提交是免费的。大提交藏 bug、回滚很疼。 |
| "特性开关我等会再加" | 特性没做完就不该被用户看到。现在就加开关。 |
| "这个重构很小，能放进去" | 重构混进功能让两者都更难审、更难 debug。拆开。 |
| "我再跑一次构建确认一下" | 一次成功跑过之后，重跑同一条不会增加信心，除非代码有变。改完再跑，不是求安慰。 |

## 红旗

- 跑了 100+ 行还没测
- 一条增量里塞多个不相关的改动
- "我顺手也加一点这个" ， 范围扩张
- 跳过测 / 验步骤去抢速度
- 增量之间留破损的构建或测试
- 大量改动未提交
- 在第三个用例出现之前就建抽象
- 跑任务范围之外的"顺手改"
- 为一次性动作新建工具文件
- 在没有任何代码改动之间，重跑同一条构建 / 测试命令两次

## 验证

为一项任务走完所有增量后：

- [ ] 每个增量都单独测过并提交
- [ ] 完整测试套件通过
- [ ] 构建是干净的
- [ ] 功能端到端按规格工作
- [ ] 没有未提交的改动

## 参见

每个增量的验证只是局部检查。在宣告任务完成前，先套用项目级的 Definition of Done 作为最终门槛 ， 那是任何增量都要越过的常设 bar，无论任务是什么。参见 `../../references/definition-of-done.md`。
