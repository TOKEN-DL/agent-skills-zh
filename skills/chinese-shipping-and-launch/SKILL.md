# Shipping and Launch

## 概述

稳稳地上线。目标不只是部署 ， 是要安全地部署，监控到位，回滚方案备好，对"什么算成功"有清晰的认知。每次上线都应该是可逆的、可观察的、渐进的。

## 何时使用

- 首次把特性部署到生产
- 给用户发布重大变更
- 做数据或基础设施迁移
- 开 beta / early access
- 任何带风险的上线（都是）

## 上线前清单

### 代码质量

- [ ] 全部测试通过（单元、集成、E2E）
- [ ] 构建成功无警告
- [ ] Lint 和类型检查通过
- [ ] 已评审并批准
- [ ] 没有应该在上线前就解决的 TODO
- [ ] 生产代码里没有 `console.log` 调试语句
- [ ] 错误处理覆盖了预期的失败模式

### 安全

- [ ] 代码或版本控制里没有密钥
- [ ] 该生态的依赖审计（`npm audit`、`pip-audit`、`cargo audit` 等）没有 critical 或 high 漏洞
- [ ] 所有面向用户的 endpoint 都有输入校验
- [ ] 认证与授权检查到位
- [ ] 安全响应头已配置（CSP、HSTS 等）
- [ ] 认证端点有限流
- [ ] CORS 仅对具体来源开放（非通配符）

### 性能

- [ ] Core Web Vitals 处于 "Good" 区间
- [ ] 关键路径没有 N+1 查询
- [ ] 图片已优化（压缩、响应式尺寸、懒加载）
- [ ] bundle 在预算内
- [ ] 数据库查询有合适的索引
- [ ] 对静态资产和重复查询配了缓存

### 可访问性

- [ ] 所有交互元素都支持键盘
- [ ] 屏幕阅读器能传达页面内容与结构
- [ ] 颜色对比达到 WCAG 2.1 AA（文本 4.5:1）
- [ ] 模态与动态内容的焦点管理正确
- [ ] 错误信息具体且关联到表单字段
- [ ] axe-core 或 Lighthouse 没有可访问性告警

### 基础设施

- [ ] 环境变量在生产侧已设
- [ ] 数据库迁移已应用（或准备好应用）
- [ ] DNS 与 SSL 已配置
- [ ] CDN 已对静态资产配置
- [ ] 日志与错误上报已配置
- [ ] 健康检查端点存在并能响应

### 文档

- [ ] README 已更新以反映新设置要求
- [ ] API 文档是当前的
- [ ] 架构决策已写过 ADR
- [ ] Changelog 已更新
- [ ] 用户侧文档已更新（如适用）

## 特性开关策略

放在特性开关后面发布，把部署和发布解耦：

```typescript
// 特性开关检查
const flags = await getFeatureFlags(userId);

if (flags.taskSharing) {
  // 新特性：任务分享
  return <TaskSharingPanel task={task} />;
}

// 默认：既有行为
return null;
```

**特性开关生命周期：**

```
1. 部署（开关 OFF）     → 代码已上生产但未激活
2. 给团队 / beta 用户开启  → 在生产环境里做内部测试
3. 渐进放量             → 5% → 25% → 50% → 100% 用户
4. 每阶段监控             → 关注错误率、性能、用户反馈
5. 清理                → 完全放量后清除开关与死代码路径
```

**规则：**
- 每个特性开关有负责人与过期日期
- 完全放量后 2 周内清理
- 不要嵌套特性开关（组合数爆炸）
- CI 里同时测两种开关状态（开 / 关）

## 分阶段放量

### 放量顺序

```
1. 部署到 staging
   └── 在 staging 环境跑全量测试
   └── 手工冒烟关键流程

2. 部署到生产（特性开关 OFF）
   └── 验证部署成功（健康检查）
   └── 看错误监控（没有新错误）

3. 给团队开启（开关对内部用户 ON）
   └── 团队在生产环境用上这个特性
   └── 24 小时监控窗口

4. Canary 放量（5% 用户开关 ON）
   └── 监控错误率、延迟、用户行为
   └── 对比 canary 与基线指标
   └── 24-48 小时监控窗口
   └── 只有全部阈值通过才推进（见下表）

5. 渐进扩大（25% → 50% → 100%）
   └── 每步做同样监控
   └── 任意时刻都能回到上一档

6. 全量放量（对所有用户开关 ON）
   └── 监控 1 周
   └── 清理特性开关
```

### 放量决策阈值

用以下阈值决定每个阶段是推进、保持还是回滚：

| 指标 | 推进（绿） | 保持并排查（黄） | 回滚（红） |
|--------|-----------------|-------------------------------|-----------------|
| 错误率 | 距基线 ±10% 以内 | 高出基线 10-100% | 高出基线 2 倍以上 |
| P95 延迟 | 距基线 ±20% 以内 | 高出基线 20-50% | 高出基线 50% 以上 |
| 客户端 JS 错误 | 没有新错误类型 | 新错误在 <0.1% 的会话 | 新错误在 >0.1% 的会话 |
| 业务指标 | 中性或向好 | 下降 <5%（可能是噪声） | 下降 >5% |

### 何时回滚

出现下列情况立即回滚：
- 错误率上升超过基线 2 倍
- P95 延迟上升超过 50%
- 用户反馈的问题飙升
- 检测到数据完整性问题
- 发现安全漏洞

## 监控与可观测性

### 监控什么

```
应用层指标：
├── 错误率（总、按 endpoint）
├── 响应时间（p50、p95、p99）
├── 请求量
├── 活跃用户
└── 关键业务指标（转化、参与度）

基础设施层指标：
├── CPU 和内存使用
├── 数据库连接池用量
├── 磁盘空间
├── 网络延迟
└── 队列深度（如适用）

客户端指标：
├── Core Web Vitals（LCP、INP、CLS）
├── JavaScript 错误
├── 客户端视角的 API 错误率
└── 页面加载时间
```

### 错误上报

```typescript
// 设置带上报的 error boundary
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 上报到错误追踪服务
    reportError(error, {
      componentStack: info.componentStack,
      userId: getCurrentUser()?.id,
      page: window.location.pathname,
    });
  }

  render() {
    if (this.state.hasError) {
      return <ErrorFallback onRetry={() => this.setState({ hasError: false })} />;
    }
    return this.props.children;
  }
}

// 服务端错误上报
app.use((err: Error, req: Request, res: Response, next: NextFunction) => {
  reportError(err, {
    method: req.method,
    url: req.url,
    userId: req.user?.id,
  });

  // 不要向用户暴露内部细节
  res.status(500).json({
    error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' },
  });
});
```

### 上线后验证

上线后的第一小时：

```
1. 健康端点返回 200
2. 看错误监控面板（没有新错误类型）
3. 看延迟面板（没有回归）
4. 手动测关键用户流程
5. 验证日志在流动、可读
6. 确认回滚机制可用（能 dry-run 就 dry-run）
```

## 错误预算放行闸

服务的错误预算 ， SLO 允许失败的那部分请求或时间 ， 决定了能否安全发布。把它当作客观的闸 ， 而不是谈判：

```
剩余预算 > 20%   → 正常上线；密切监控
剩余预算 0-20%   → 只做慢放量；不做高风险改动
预算耗尽          → 冻结特性工作；全力保可靠性
预算重置          → 恢复正常节奏；把恢复的那次 bug fix 沉淀进流程
```

在 canary 阶段的高燃烧率（比基线消耗更快）就是上面放量阈值表里的"保持"信号 ， 与错误率上升的待遇一样。

## 回滚策略

每次部署都要先有回滚方案：

```markdown
## Rollback Plan for [Feature/Release]

### Trigger Conditions
- 错误率 > 基线 2 倍
- P95 延迟 > [X] ms
- 收到 [具体问题] 的用户报告

### Rollback Steps
1. 关闭特性开关（如适用）
   OR
1. 部署上一版：`git revert <commit> && git push`
2. 验证回滚：健康检查、错误监控
3. 通报：通知团队回滚已完成

### Database Considerations
- 迁移 [X] 有回滚方案：<已校验的命令或运行书链接>
- 新特性写入的数据：[保留 / 清理]

### Time to Rollback
- 特性开关：< 1 分钟
- 重新部署上一版：< 5 分钟
- 数据库回滚：< 15 分钟
```

## 常见借口

| Rationalization | Reality |
|---|---|
| "在 staging 能跑，生产也能跑" | 生产的数据、流量模式、边界情况都不同。上线后要监控。 |
| "这个不需要特性开关" | 每个特性都受益于 kill switch。连"简单"改动都可能出岔子。 |
| "监控就是 overhead" | 没有监控意味着你要从用户投诉里发现问题，而不是从面板上。 |
| "监控我等会再加" | 上线前就加。没有可视化就没法 debug。 |
| "回滚就是认栽" | 回滚才是负责的工程。上线一个坏特性才是失败。 |
| "错误率看起来 OK，继续上" | 看燃烧率，不只看当前错误率。比基线耗得更快的预算就是"保持"信号，即便各项阈值仍然绿。 |

## 红旗

- 没回滚方案就部署
- 生产里没有监控或错误上报
- 一锤子发布（一把全上，没有 staging）
- 特性开关没有过期日或负责人
- 上线第一小时没人盯着
- 生产环境配置靠记性而不是代码
- "周五下午了，上吧"
- 错误预算耗尽但功能工作照样推进

## 验证

上线前：

- [ ] 上线前清单走完（所有项绿）
- [ ] 特性开关已配置（如适用）
- [ ] 回滚方案已文档化
- [ ] 监控面板已搭好
- [ ] 团队已知会这次部署

上线后：

- [ ] 健康检查返回 200
- [ ] 错误率正常
- [ ] 延迟正常
- [ ] 关键用户流程跑通
- [ ] 日志在流
- [ ] 回滚已测试或确认可用

对每个已发布服务：

- [ ] 错误预算策略已落地：预算低于 20% 与耗尽时各自该做什么心里有数
