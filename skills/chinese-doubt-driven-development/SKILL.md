# Doubt-Driven Development

## 概述

一个自信的答案并不就是正确的答案。长会话积累的上下文会把假设悄悄变成"事实"，没人察觉。质疑驱动开发（Doubt-driven development）就是一份纪律 ， 在每个非平凡的产出站住前，先具化出一个 fresh-context 的评审者，让它偏向**证伪**而不是赞同。

这不是 `/review`。`/review` 是对成品的判定。这是一种飞行中的姿态：非平凡决策在被交叉质询时，方向修正还便宜。

## 何时使用

满足下列任一就启用 ， 这就是**非平凡的**：

- 它引入或修改分支逻辑
- 它跨越模块或服务边界
- 它断言了一种类型系统或编译器无法验证的属性（线程安全、幂等性、顺序、不变量）
- 它的正确性取决于未来读者看不到的上下文
- 它的爆炸半径是不可逆的（生产部署、数据迁移、公开 API 变更）

在以下时机应用：

- 要在不确定性下做架构决策
- 要提交非平凡代码
- 要宣称一条非显然事实（"这是安全的"、"这能 scale"、"这匹配规格"）
- 在没完全理解的代码里工作

**何时不用：**
- 机械操作（重命名、格式化、文件移动）
- 跟着清晰、无歧义的用户指令
- 读或总结既有代码
- 正确性显而易见的一行改动
- 纯工具型操作（跑测试、列文件）
- 用户明确要速度而非验证

如果对每个按键都质疑，你什么都发不出去。这个 Skill 只适用于上面定义的非平凡决策。

## 加载约束

这个 Skill 设计给**主会话编排者**，在那里步骤 3（DOUBT，下详）能派生一个 fresh-context 评审者。

- **不要把这个 Skill 加到角色的 `skills:` frontmatter。** 一个会执行步骤 3 的角色就会派生另一个角色 ， 这正是 `../../references/orchestration-patterns.md` 明确禁止的编排反模式（"角色不调用其它角色"）。
- **如果你发现自己是在 subagent 上下文里**（Claude Code 禁掉嵌套派生 subagent 时）应用这个 Skill：首选路径是向用户报告 doubt-driven 不能嵌套运行，让主会话处理。作为最后手段，存在一个退化的"自我质疑"回退 ， 把 ARTIFACT + CONTRACT 写成一个全新的自我 prompt 和原有推理之间的硬心理隔断，然后跑步骤 1-5。**这不是 fresh-context 评审**（你带着自己的上下文），所以要把结果标注为退化版，只要用户能触达就优先升级。

## 流程

应用这个 Skill 时把这份清单拷过去：

```
Doubt cycle:
- [ ] 步骤 1：CLAIM ， 写出声明 + 它为什么重要
- [ ] 步骤 2：EXTRACT ， 隔离出 artifact + contract，剥离推理
- [ ] 步骤 3：DOUBT ， 用对抗式 prompt 调起 fresh-context 评审者
- [ ] 步骤 4：RECONCILE ， 对照 artifact 文本对每条发现分类
- [ ] 步骤 5：STOP ， 满足停止条件（平凡发现、3 轮、或用户覆盖）
```

### 步骤 1：CLAIM ， 把"正站着的"亮出来

用两到三行命名决策：

```
CLAIM：新的缓存层在规格描述的"读多写少"负载下是线程安全的。
为什么重要：这里的竞争破坏用户数据，且在 QA 里难发现。
```

如果你没法把声明压缩到这么短，那不是决策，是氛围。在审视前先把它亮出来。

### 步骤 2：EXTRACT ， 最小可审单元

fresh-context 评审者需要的是 **artifact** 与 **contract**，不是走过场。

- 代码：diff 或函数 ， 不是整个文件
- 决策：3-5 句提议 + 它必须满足的约束
- 断言：宣称的事实 + 所谓支持的证据（与步骤 1 的 CLAIM 块分开保留 ， CLAIM 是编排者要审视的假设）

把推理剥掉。如果交付的是结论，收到的就是对你结论的赞同。单元必须小到评审者读一遍就能 hold 住 ， 如果是 500 行的 PR，先拆。

### 步骤 3：DOUBT ， 调起 fresh-context 评审者

评审者 prompt **必须是对抗式**。框定决定答复。

```
对抗式评审。找出这份 artifact 哪里不对。
假设作者过度自信。重点找：
- 没明说的假设
- 没处理的边界情况
- 隐藏的耦合或共享状态
- 契约可能被违反的方式
- 这次可能打破的既有约定
- 在意外输入下的失败模式

不要确认。不要总结。找出问题，或者在彻底审视
后明确说找不到。

ARTIFACT：<粘贴 artifact>
CONTRACT：<粘贴 contract>
```

**只传 ARTIFACT + CONTRACT。 不要传 CLAIM。** 把结论给评审者会把它往赞同那边偏。评审者必须独立判定 artifact 是否满足 contract。

在 Claude Code 中，`agents/` 里那些按角色组织的评审者天生从隔离上下文开始，可以在这里用 ， 看 `agents/` 找角色清单与按领域匹配。

**上面的对抗式 prompt 优先于角色的默认响应形态。** 像 `code-reviewer` 这类角色被写成产生"发现 + 优点"并存的平衡判定；doubt-driven 需要只挑问题的输出。把对抗式 prompt **原样**贴进调用，让它盖过角色默认。如果某个角色的响应形态没法干净盖过，就用一个带对抗式 prompt 的通用 subagent 兜底。

#### 跨模型升级

单一模型评审者与原作者共享盲点 ， 一个更冷、不同架构的模型能抓到。doubt-driven 已经对非平凡决策自动启用，所以在这之内提供跨模型属于它价值的一部分，不是可选摩擦。

**交互式会话：永远提供。 不要悄悄跳过。**

**步骤 1：问用户**

在步骤 3 的单模型评审后、RECONCILE 前，停一下问：

> *"单模型评审完成。要不要跨模型的第二意见？选项：Gemini CLI、Codex CLI、手工外部评审（你把它粘到别处），或者跳过。"*

这个问题在每次交互式 doubt cycle 都是强制的 ， 即便感觉是低风险的。决定权在用户，不在 Agent。Agent 的职责是把选项浮出来。

**步骤 2：如果用户选了 CLI ， 验证，再调用**

1. 检查工具是否在 PATH 里（`which gemini`、`which codex`）。
2. 先测试它能用（`gemini --version` 等）再传完整 prompt ， 一个过时或坏掉的二进制可能过 `which` 但在真输入上挂掉。
3. 与用户确认准确的调用，包括必需的 flags、鉴权与环境变量（例如 API key）。各家实现不一样，永远不要假设。
4. 只传 ARTIFACT + CONTRACT + 对抗式 prompt。**不传任何会话上下文，不传 CLAIM。**
5. 注意 shell 转义。如果 artifact 含有引号、`$(...)` 或反引号，优先 stdin（`echo … | gemini`）或 heredoc 而不是 inline `-p "…"`。拿不准就先与用户确认调用再跑。
6. 把输出带到步骤 4（RECONCILE）。

**永远不要把 artifact 内插到一个 shell 引号参数里。** 代码、Markdown、review prompt 经常带反引号、`$(...)` 与引号字符，它们要么截断 prompt、要么执行内嵌的 shell。把完整 prompt 写到文件里、再用 stdin 流过去。

示例形态（先对照装好的工具核 flag ， 不同实现与版本语法各异）：

```bash
# 先把对抗式 prompt + ARTIFACT + CONTRACT 写到临时文件。
# 然后用 stdin 流过去，让 artifact 里的 shell 元字符保持惰性。

# Codex（read-only 沙盒让 CLI 不写你的工作目录）：
codex exec --sandbox read-only -C <repo-path> - < /tmp/doubt-prompt.md

# Gemini（'--approval-mode plan' 是只读；'-p ""' 触发非交互
# 模式，prompt 从 stdin 读）：
gemini --approval-mode plan -p "" < /tmp/doubt-prompt.md
```

只读沙盒是关键细节：doubt artifact 本身可能携带指令（不管是故意还是意外的 prompt injection），没有只读沙盒的话，跨模型 CLI 会照着对工作目录执行。

**步骤 3：CLI 不可用或失败时**

显式抛出失败。提供：手工跑、换一个工具、或者跳过。不要悄悄回退到单模型 ， 用户应该知道跨模型没发生。

**步骤 4：用户跳过时**

在输出里承认这次跳过（"Proceeding with single-model findings only"），然后继续到 RECONCILE。跳过可以；悄悄跳过不可以。

**非交互式上下文**（CI、`/loop`、自主循环、定时任务）：

- 跨模型**被跳过**，且必须在输出中**宣告**："Cross-model skipped: non-interactive context."
- **永远不要在没显式用户授权时调用外部 CLI** ， 这是关键的安全属性。

跨模型带来开销、延迟和工具脆弱性。Agent 在每次循环把选项浮出来；用户决定要不要为这份 artifact 付出。

### 步骤 4：RECONCILE ， 把发现折回

评审者的输出是数据，不是裁决。**你仍是编排者。** 在分类前再读一遍 artifact 文本 ， 跟着评审者走就是忽略评审者同样错误的失效模式。

对每条发现，按这个**优先级**分类（先命中的类胜出）：

1. **契约误读** ， 评审者挑出问题只是因为你给的 CONTRACT 不清晰或不完整。先修 CONTRACT，下一轮再分类。
2. **有效且可执行** ， 真问题需要改 artifact。改它，再下一轮。
3. **有效取舍** ， 问题真但修起来的代价大于接受的代价。把取舍明确写下来，让用户看到。
4. **噪声** ， 评审者挑出了问题，实际上在评审者看不到的上下文里是对的。记下来，跳过，并问：把那条上下文加到 CONTRACT 能不能避免误报？

一个新鲜的评审者会因为缺上下文而错。不要光因为它"fresh"就 defer。

### 步骤 5：STOP ， 有界循环，不是递归

在以下任一条件停下：

- 下一轮只返回平凡或已被覆盖过的发现，**或者**
- 已跑 3 轮（升级到用户，别自己磨第四轮），**或者**
- 用户明确说"ship it"

如果跑了 3 轮评审者还在挑实质性问题，artifact 可能没准备好。把这件事告诉用户 ， 三轮未解决的循环，是对 artifact 的信息，不是继续循环的理由。

如果 3 轮"显然不够"是因为 artifact 太大：artifact 太大了 ， 回到步骤 2 拆。不要取消限制。

## 常见借口

| Rationalization | Reality |
|---|---|
| "我自信了，跳过质疑" | 在新问题上，自信与正确性的相关性很低。正是笃定的瞬间藏着盲点。 |
| "派生一个评审者代价高" | 在生产里 debug 一个错误提交代价更高。检查有界；bug 无界。 |
| "评审者只会抠 nit" | 没框范围时才会。把 prompt 限定到"按 contract 算会失败的点"。 |
| "我放在最后用 `/review` 做质疑" | `/review` 是最后一道闸。Doubt-driven 在方向还便宜时抓错方向。到 PR 阶段就晚了。 |
| "我对每一步都质疑，那就发不出了" | 这个 Skill 只针对非平凡决策，不是每个按键。重读"何时不用"。 |
| "两种意见总比一种好" | 当第二种意见上下文更少、产生噪声的时候不是。Reconcile，不要 defer。 |
| "评审者不同意，那就我错了" | 评审者缺你的上下文 ， 不同意是信息，不是裁决。再读 artifact，分类，再决定。 |
| "跨模型总是更好" | 跨模型能抓到单模型与自身共享的盲点，但加上代价与工具脆弱性。每次交互式循环都给出选项 ， 用户决定 artifact 值不值。Agent 的职责是浮出选择，而不是把门。 |
| "用户说过一次'是'，那我能反复调用 CLI" | 每次调用都是独立授权。artifact、prompt 与 flags 在每次调用都不同 ， 每次跑前与用户重新确认那一条确切命令。 |

## 红旗

- 为了重命名或格式化改动派生 fresh-context 评审者
- 不再读 artifact 文本就把评审者输出当权威
- 跑 >3 轮循环却不升级到用户
- 用"这好吗？"而不是"找问题"来 prompt 评审者
- 时间压力下跳过对高风险决策的质疑
- 对未改动的 artifact 再派生 fresh-context（你会收到一样的发现；在拖时间）
- **质疑走过场（可验证信号）**：在 2 个或更多循环中评审者都挑出了实质问题，但 0 条发现被分类为可执行。是在确认，不是质疑。停下来升级。
- 只在提交后才质疑 ， 那是 `/review`，不是质疑驱动开发
- 硬编码一个外部 CLI 调用而不与用户确认该工具存在、已配置、接受那套确切语法
- **在交互式 doubt cycle 中悄悄跳过跨模型。** 即便不推荐，提供也得可见。跳过可以；悄悄跳过不可以。
- 外部 CLI 报错或缺失时悄悄回退 ， 把失败亮出来，让用户改道
- 从评审者输入里把 contract 剥掉
- 把 CLAIM 传给评审者（把它往赞同那边偏）

## 与其它 Skill 的协作

- **`code-review-and-quality` / `/review`**：互补。`/review` 是事后对 PR 的判定；doubt-driven 是飞行中、按决策的。两边都用。
- **`source-driven-development`**：SDD 对照官方文档核验"关于框架的事实"。Doubt-driven 核验"你关于 artifact 的推理"。SDD 检查 API 存在；doubt-driven 检查你在 contract 下是否正确使用了它。
- **`test-driven-development`**：TDD 的 RED 步就是把质疑具体化 ， 一条失败的测试就是一次证伪尝试。当 TDD 适用时，那条失败的测试*就是*对行为声明的质疑步。
- **`debugging-and-error-recovery`**：当评审者挑出真实失败模式时，掉进 debugging skill 做定位与修复。
- **仓库编排规则**（`../../references/orchestration-patterns.md`）：这个 Skill 由主会话编排。一个角色调用另一个角色是反模式 B ， 见上文加载约束。

## 验证

应用 doubt-driven development 后：

- [ ] 每个非平凡决策（按上文定义）都被明确命名为 CLAIM 才站住
- [ ] 每个非平凡 artifact 至少被一次 fresh-context 评审（TDD 的 RED 步产出的失败测试对行为声明满足这一点，见上文的协作）
- [ ] 评审者拿到的是 ARTIFACT + CONTRACT ， 不是 CLAIM，不是你的推理
- [ ] 评审者 prompt 是对抗式的（"找问题"），不是赞同式的（"好不好"）
- [ ] 各种发现被对照 artifact 文本分类（而非走过场）使用优先级：契约误读 / 可执行 / 取舍 / 噪声
- [ ] 满足停止条件（平凡发现、3 轮、或用户覆盖）
- [ ] 在交互式模式下，跨模型被**显式提供给用户**（无论 artifact 风险如何）且回复在输出中得到了承认
- [ ] 在非交互式模式下，跨模型被跳过且宣布跳过
- [ ] 任何外部 CLI 调用之前都做了 PATH 检查、能用二进制测试、与用户核对语法、并显式授权运行
