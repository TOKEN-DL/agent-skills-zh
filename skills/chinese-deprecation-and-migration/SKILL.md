# Deprecation and Migration

## 概述

代码是负债而非资产。每一行代码都有持续维护成本 ， bug 要修、依赖要更新、安全补丁要打，还有新人要带。弃用是移除"不再挣回维护成本"的代码的纪律，迁移是把用户从旧系统安全搬到新系统的过程。

大多数工程组织擅长造东西。很少有擅长拆东西的。这个 Skill 就来补这块短板。

## 何时使用

- 用新系统、API 或库替换旧的
- 下线不再需要的特性
- 整合重复实现
- 删除没人拥有但人人都依赖的死代码
- 规划新系统的生命周期（弃用规划在设计阶段就该开始）
- 决定到底是要维护遗留系统还是投资迁移

## 核心原则

### 代码是负债

每一行代码都有持续成本：它要测试、要文档、要打安全补丁、要更新依赖、还要让旁边的任何人在心里多背一份。代码的价值在于它提供的功能、不是代码本身。当同样的功能可以用更少代码、更简单复杂度或更好的抽象提供时 ， 旧代码就该走。

### Hyrum 定律让删除难

用户足够多时，所有可观测行为都会被依赖 ， 包括 bug、时序怪癖和未文档化的副作用。这就是为什么弃用需要主动迁移，而不是仅仅公告。用户没法"直接切"，因为他们依赖那些替代品不会复现的行为。

### 弃用规划在设计阶段就开始

造新东西时，问一句："3 年后怎么把它拆掉？" 用干净接口、特性开关、最小表面积设计的系统，比那些到处泄露实现的系统更容易弃用。

## 弃用决策

在弃用任何东西之前，先答这些问题：

```
1. 这套系统还在提供独立的价值吗？
   → 是，就维护。不是，进到下一步。

2. 有多少用户 / 消费者依赖它？
   → 量化迁移的范围。

3. 有替代品吗？
   → 没有就先建替代品。不要在没有替代方案时弃用。

4. 每个消费者的迁移成本是多少？
   → 如果可以自动完成，就做。如果要手工且花力气，就和持续维护成本比一下。

5. 不弃用的持续维护成本是什么？
   → 安全风险、工程师时间、复杂度带来的机会成本。
```

## 强制 vs 顾问式弃用

| 类型 | 何时用 | 机制 |
|------|-------------|-----------|
| **顾问式** | 迁移可选，旧系统稳定 | 警告、文档、推一下。用户按自己的时间表迁。 |
| **强制** | 旧系统有安全问题、阻塞进展或维护成本不可持续 | 硬期限。旧系统将在 X 日被移除。提供迁移工具。 |

**默认走顾问式。** 只有维护成本或风险到了一定程度才用强制。强制弃用需要提供迁移工具、文档和支持 ， 不能只通告一个截止日期。

## 迁移流程

### 步骤 1：先把替代品建好

不要在没工作的替代方案时弃用。替代品必须：

- 覆盖旧系统的全部关键用例
- 有文档与迁移指南
- 在生产中已证明（不是只是"理论上更好"）

### 步骤 2：通告并文档化

```markdown
## Deprecation Notice: OldService

**Status:** 自 2025-03-01 起弃用
**Replacement:** NewService（见下方迁移指南）
**Removal date:** 顾问式 ， 暂无硬截止
**Reason:** OldService 需要手工扩缩容、缺乏可观测性。
            NewService 自动处理两者。

### Migration Guide
1. 把 `import { client } from 'old-service'` 换成 `import { client } from 'new-service'`
2. 更新配置（见下方示例）
3. 跑迁移验证脚本：`npx migrate-check`
```

### 步骤 3：增量迁移

把消费者一个一个迁，而不是所有人一起。对每个消费者：

```
1. 列出与弃用系统的全部接触点
2. 改为走替代品
3. 验证行为匹配（测试、集成检查）
4. 拿掉对旧系统的引用
5. 确认没有回归
```

**Churn 规则：** 如果你拥有要弃用的基础设施，那把用户迁过去就是你的责任 ， 或者提供无需迁移的向后兼容更新。不要发个弃用通告就让用户自己想办法。

### 步骤 4：移除旧系统

只在所有消费者都已迁完之后再移除：

```
1. 验证零活跃使用（指标、日志、依赖分析）
2. 删代码
3. 删关联测试、文档与配置
4. 删弃用通告
5. 庆祝 ， 删代码是成就
```

## 迁移模式

### Strangler 模式

新系统与旧系统并行跑。按阶段把流量从旧导到新。当旧系统承担 0% 流量时，把它移除。

```
阶段 1：新系统承担 0%，旧系统承担 100%
阶段 2：新系统承担 10%（金丝雀）
阶段 3：新系统承担 50%
阶段 4：新系统承担 100%，旧系统空闲
阶段 5：移除旧系统
```

### Adapter 模式

造一个适配器把从旧接口的调用翻译给新实现。消费者继续用旧接口，你同时迁移后端。

```typescript
// 适配器：旧接口，新实现
class LegacyTaskService implements OldTaskAPI {
  constructor(private newService: NewTaskService) {}

  // 旧方法签名，委托给新实现
  getTask(id: number): OldTask {
    const task = this.newService.findById(String(id));
    return this.toOldFormat(task);
  }
}
```

### 特性开关迁移

用特性开关把消费者一个一个从旧切到新：

```typescript
function getTaskService(userId: string): TaskService {
  if (featureFlags.isEnabled('new-task-service', { userId })) {
    return new NewTaskService();
  }
  return new LegacyTaskService();
}
```

### 数据库 Schema 迁移（Expand/Contract）

Schema 变更是风险最高的迁移，因为数据是无法靠回滚部署救回的东西。失效模式是把 schema 变更和代码变更绑死：同一版本改名列名同时改读列名的代码，于是发布窗口里 ， 旧代码和新代码同时在线 ， 有一方在读不存在的列。修法是**永远不要原地改列**。分加性阶段迁，让旧新代码在每一步都合法。

```
EXPAND ──────────────→ MIGRATE ──────────────→ CONTRACT
加新列（可空），与       把已有行回填，应用      一旦没有代码再读
旧列并存               开始同时双写旧+新         旧列，单独后续发布
                                                  里把它删掉
```

**示例 ， 把 `name` 改成 `full_name`：**

1. **Expand。** 加 `full_name`，可空。部署。（旧代码忽略它，没事。）
2. **双写。** App 在每次 insert/update 同时写 `name` 和 `full_name`。部署。
3. **回填。** 把 `name → full_name` 对存量行做回填，分批，别锁表。
4. **切读。** 把 App 切到读 `full_name`，继续双写。部署，跑一会儿。
5. **Contract。** 停止写 `name`，然后 ， 在一个*独立的、稍后的*发布里 ， 把列删了。

每一步独立可部署、可回滚：如果第 4 步异常，回滚代码后 `full_name` 还在被填。把每一阶段当作一条细纵切片 ， 见 `incremental-implementation` Skill。

**规则：**
- **先加性，后破坏性，且最后单独。** 加（新可空列、新表、新索引）在任何发布都安全；删与重命名等到没有代码读旧形态时再独立发布。
- **每个迁移都要有测试过的 down 路径。** 一个无法回滚的迁移就是无法回滚的部署。在合并前写好并跑一次 `down`。
- **回填分批，在热路径之外。** 对百万行做一次 `UPDATE` 会锁表；分块再节流。
- **建大索引时别阻塞写**（如 Postgres `CREATE INDEX CONCURRENTLY`）。
- **走特性开关把代码解耦** 当割接有风险时，与"特性开关迁移"模式完全一致。

## 僵尸代码

僵尸代码是没人拥有但人人依赖的代码。它不被主动维护、没有明确负责人、堆积安全漏洞与兼容问题。信号：

- 6 个月以上没提交但有活跃消费者
- 没有指定的维护人或团队
- 测试挂了没人修
- 依赖有已知漏洞但没人更
- 文档引用的系统早已不存在

**应对：** 要么指定一个负责人好好维护，要么用一份具体的迁移计划弃用它。僵尸代码不能留在 limbo 里 ， 要么投资要么移除。

## 常见借口

| Rationalization | Reality |
|---|---|
| "还能用，为什么要删？" | 没人维护却能用的代码会堆积安全债与复杂度。维护成本静悄悄长大。 |
| "以后可能有人要用" | 如果以后需要，可以重建。为了"以防万一"留不用的代码，比重建贵。 |
| "迁移太贵了" | 把迁移成本和未来 2-3 年的持续维护成本对一下。长期来看迁移通常更便宜。 |
| "新系统搞完后再弃用" | 弃用规划在设计阶段就开始。新系统搞完时，你又有新优先级了。现在就规划。 |
| "用户会自己迁" | 不会。提供工具、文档、激励 ， 或者自己迁（Churn 规则）。 |
| "我们可以无限维护两套系统" | 两套系统做同一件事，维护、测试、文档、新人带 ， 都得乘二。 |
| "重命名这个列就是一行的事" | 发布期新旧代码同时跑 ， 有一方在读已经不存在的列。用 expand/contract，不要原地重命名。 |
| "我加列、在同一条迁移里删旧的" | 把"安全加列"绑死了"破坏性删列"。删要在自己独立发布里，且不能有代码读旧形态时再做。 |
| "我们用得着再写回滚" | 没 down 路径的迁移是不可回滚的部署。在合并前写好并跑 down。 |

## 红旗

- 弃用了但没替代品
- 弃用通告但没迁移工具或文档
- "软"弃用好几年没进度
- 僵尸代码没负责人却有活跃消费者
- 给弃用系统加新特性（应投到替代品）
- 弃用时没量过当前用量
- 删代码时没确认零活跃消费者
- schema 变更与依赖它的代码在同一次发布
- 列被原地重命名或删除而不是走 expand/contract
- 合并时迁移没测试过的 down 路径，或回填会锁表

## 验证

完成弃用后：

- [ ] 替代品在生产中被证明、覆盖全部关键用例
- [ ] 迁移指南存在，含具体步骤与示例
- [ ] 所有活跃消费者都已迁移（用指标 / 日志核过）
- [ ] 旧代码、测试、文档与配置被完整移除
- [ ] 代码库里没有对弃用系统的引用
- [ ] 弃用通告被移除（它完成了使命）

数据库 schema 迁移后：

- [ ] 变更以加性阶段（expand → backfill → contract）发布，而不是单次原地编辑
- [ ] 旧新代码在每一次发布时都对当前 schema 合法
- [ ] 每个迁移有测试过的 down 路径；回填以节流分批跑
- [ ] 破坏性步骤（删 / 重命名）在自己的发布里、且没有代码再读旧形态时才上
