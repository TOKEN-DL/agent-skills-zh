# Interview Me

## 概述

人们嘴上要的和他们真正想的是两件事。他们说"做个 dashboard"，因为这是该说的话，不是因为 dashboard 解决了他们的问题。他们说"让它更快"，但没说要打到多少 ms。

发现这段差距的最便宜时刻，是任何计划、规格、代码出现**之前**。一旦开始建，转向成本是真的，并且用户会把错的东西合理化为"差不多就那样"。错配就被锁死了。

这个 Skill 在还没造成任何成本前把差距关上。其它 Define 阶段的 Skill 假设你已经大致知道要什么：`idea-refine` 由一个想法生成变体，`spec-driven-development` 把需求写下来，`doubt-driven-development` 在你写好规划后再压力测试。interview-me 是它们共同的前置 ， 你一次问一个问题、加上你的最佳猜测，直到能在用户说出来之前预测出他要说什么。

## 何时使用

满足下列任一就启用：
- 请求里至少缺一个：**谁**要、**为什么**要、成功**长什么样**、绑定的**约束**是什么
- 请求是常见的而非具体的（"给我做个 X"、"让它更快"），你不拆开惯例就只能猜
- 你忍不住要先靠未说出来的假设往下走
- 当两个合理的取舍项（简单 vs 灵活、成本 vs 速度）摆在面前，用户没说他在优化哪个值
- 用户显式触发："interview me"、"grill me"、"开工前咱们确实下？"、"stress-test my thinking"

**不要用：**
- 请求明确、自成一体（"重命名这个变量"、"修这个 typo"）
- 用户已经明确要速度不要验证
- 单纯信息请求（"X 怎么工作？"、"这段代码干嘛的？"）
- 机械操作（重命名、格式化、文件移动）
- 你已经有 ≥95% 置信度；先重读下面的停止条件再判断

## 加载约束

这个 Skill 需要一个活的、能回应的用户。**不要在非交互式上下文（CI 流水线、定时任务、`/loop`、autonomous-loop）里调用。** 当你在这些场景且请求欠规格时，把它当作阻塞问题向用户报告，不要靠猜继续。

## 流程

### 步骤 1：先有假设，并标个置信度

在提问之前，先用**一句话**写下你当前对用户想要什么的最佳解读，外加一个诚实的置信度（0-100%）：

```
假设 (HYPOTHESIS)：你想要一种回答 "我们做得怎么样？" 的方式，
                   而 "dashboard" 是你能想到的惯例话术。
置信度 (CONFIDENCE)：~30% ， 还缺：这是给谁、"metrics" 在
                       这个上下文里指什么、成功长什么样
```

数字强迫诚实。如果你写下高数字，但实际预测不出用户对接下来三个问题的反应，那这个数字就是错的。给出你能为之辩护的置信度。

当置信度低于 ~70% 时，在同一行后附一句简短的"还缺什么"理由 ， 告诉用户这次访谈要打捞什么，防止数字变成含糊的信号。

### 步骤 2：一次只问一个问题，每个问题附上你的猜测

格式：

```
Q: <一个聚焦的问题>
GUESS: <你对这个答案的猜测，以及为什么这么猜>
```

等用户反应后再问下一个。

**为什么一次一个，不批量：**
- 用户没法对你的猜测做反应，如果你把它们埋在一份清单里
- 批量鼓励走马观花和敷衍
- 第三个问题常常取决于第一个；一次性问就把框架锁死了
- 用户认真思考的能量是有限的；一次一个问题花掉它

**为什么附上猜测：**
- 对一个错的猜测作出反应，比凭空想出答案更快
- 它让你表面化了一个能"显错"的假设，让自己更诚实
- 它把**你的**假设亮了出来，这正是这次访谈要暴露的

这里的风险是有礼貌的用户为了"顺你"就附和你。缓解方法是显式地允许自己错，偶尔猜一个你预期用户会反驳的方向。

### 步骤 3：盯住"想要 vs 应想要"

最危险的答案是用户说出"听起来像正确答案"而不是他真正想要的。注意这些：
- 照"最佳实践"模板的答法（"我要可扩展"、"清晰架构"），但没有具体内容
- 把"惯例"当依据的答法（"通常应用都这么做"、"标准做法"）
- "我可能应该……"、"我觉得我应该……"、"好的工程实践说要……"
- 用 buzzword 当目标 ， "现代"、"可扩展"、"robust" 当答案，而不是具体结果

听到这些，问：

> *"如果你不需要向任何人交代，你真正想要的是什么？"*

这一个问题常常比之前五个都更管用。

### 步骤 4：用用户自己的话重述意图

当置信度高时，写回你现在的理解。保持精简（5-8 行），尽量用用户的语言，结构化以便用户逐行确认或修正：

```
我现在理解你想要的是：

- 目标 (Outcome):      <一行>
- 用户 (User):         <一行 ， 谁受益>
- 为什么是现在 (Why now):      <一行 ， 什么变了>
- 成功 (Success):      <一行 ， 怎么算这事做到了>
- 约束 (Constraint):   <一行 ， 绑定的限制>
- 不在范围 (Out of scope): <一行 ， 明确不做什么>

对 / 错 / 调整？
```

"不在范围"是**不可省略**的。错配有一半其实是对"**不**做什么"的隐性分歧。

### 步骤 5：确认 ， 明确 "是"，不是 "随你"

关口是明确的"是"。以下**不算**是：
- "随你判断" → 用户在委托，这说明他也没有 95% 置信度。换成两条具体选项重新问。
- "听起来不错" → 含糊。问："有什么要调整的？" 沉默不算确认。
- "好的，开干" → 通常是有礼貌的退出，而非认可。同样的追问。
- 沉默后说"好开始吧" → 用户放弃了访谈，不是收敛了。停下来，问问是不是漏了什么。

如果他纠正你，把修正并进来重述。直到拿到明确的"是"。

### 步骤 6：终轮 & 停止规则（关键）

当用户以明确的"是"确认了意图陈述时：

1. **给出已确认的意图陈述 (Statement of Intent)。**
2. **给出后续路径**（提议存到 `docs/intent/[topic].md`、用 `spec-driven-development` 起草规格、或者在规格完成后进入任务规划）。
3. **立即停止本轮。** 不要在这一轮调用工具、不要启动后续工作。把控制权交回用户，让他选下一步。

### 95% 置信度停止规则

你能回答"是"时算完：

> *我能预测用户对接下来我想问的三个问题的反应吗？*

如果能，你就是共识了。停下访谈、做重述。如果不能，你还没完，问下一个。

这不只是氛围，是一个可验证的测试。它也有底线：如果你已经问了好几轮依然预测不出来，那是对请求本身的信息，不是继续磨的理由。停下来告诉用户："我已经问了 X 个问题，还没法预测你的反应。有什么底层的东西我没接住。要不要回去看？"

## 产物

这个 Skill 的产物是**已确认的意图陈述**：步骤 4 的重述，加上步骤 5 的明确 "是"。这就是交付物。规格、规划、任务列表是下游，消化这个 Skill 产出的意图。

如果用户想持久化这份意图（多会话项目、交接给协作者），提议存到 `docs/intent/[topic].md`。**确认后**再保存。

## 示例

一段对比。

**不用 `interview-me`：**

```
用户：给我做个展示我们指标的 dashboard
Agent：<开始提图表库与布局>
```

Agent 已经假设了：这是给谁的、什么指标、"给我们团队"是什么意思、成功长什么样。每一个假设都是用户后面可以说"我说的不是这个"的地方。

**用 `interview-me`：**

```
用户：给我做个展示我们指标的 dashboard

Agent：
假设：你要一种在 standup 里回答 "我们做得怎么样？" 的方式，而 "dashboard"
     是你能想到的惯例话术。
置信度：~30% ， 还缺：这是给谁、"metrics" 是啥、成功长什么样

Q:    你说 "我们做得怎么样？"，是谁在问 ， 你个人、工程团队在 standup、
      还是上层（你经理、高管、董事会）？
GUESS:工程团队在 standup，因为 "我们" 通常是这个范围，且 standup 正是
       这种问题被问出来的地方。如果是给高管，指标和框架会大不一样。

用户：其实是我个人的。我老是忘了哪些实验在跑、早期信号长啥样。

Agent：
更新后的解读：根本不是团队 dashboard，是个人实验追踪器。置信度：~60%
， 还缺：什么是 "早期信号"、"完成" 长什么样

Q:    是缺了一个实验列表，还是说结果没法放到一处看？
GUESS:是后者。你某处有实验列表，但结果在五个不同的工具里，手动整合
      就是你累了想省掉的那一步。

用户：其实是前者，我连列表都没有。实验散布在不同文档里。

Agent：<继续>
```

两个问题后，Agent 发现其实要的不是一个"dashboard"，是"一个列表"。不同的产物、不同范围、不同工作。dashboard 本来就会错。

## 与其它 Skill 的协作

- **`idea-refine`**：下游。如果确认的意图是"我要 X 但不知道怎么定范围"，把它交给 `idea-refine` 来基于现已明确的意图生成变体。
- **`spec-driven-development`**：下游。如果确认的意图是具体的（"我要 X 给 Y 用户，达成 Z 成功标准"），交给它来写下来。
- **`planning-and-task-breakdown`**：本 Skill 的下两跳（先经过 spec）。
- **`doubt-driven-development`**：时间轴的相对端。interview-me 是决策前的意图抽出；doubt-driven 是决策后的产物复核。两者都在抓住分歧，但时段不同。
- **`source-driven-development`**：正交。interview-me 把"用户想要什么"问清楚；SDD 核验框架层面事实。两者不冲突。

## 常见借口

| Rationalization | Reality |
|---|---|
| "请求已经够清楚了" | 如果你现在不能用一句话写下用户想要的结果，就还不清楚。跑步骤 1 再决定。 |
| "问太多问题浪费他时间" | 4-6 个有针对性的问题浪费的时间不多。盖错楼浪费的时间极大，且承代价的是用户。 |
| "边写边弄明白" | 在代码出现之后再转方向，代价是现在的 10 倍。边写边发现是返工。 |
| "他说 '随你'，那我就定了" | "随你" 是委托不是决定。换成两条具体选项重新问。 |
| "我该列几个选项给他挑" | 当用户知道想要什么、在做取舍时，选项是有用的。他现在还不知道。列选项是加宽搜索；问问题是缩窄。 |
| "附上猜测等于带偏他" | 带偏是本意。对着猜测反应比从零想答案更快。风险是谄媚不是带偏；显式允许自己错是缓解方法。 |
| "谈得够多了，我懂了" | 自测：你能预测他对接下来三个问题的反应吗？不能就还没懂。 |
| "用户说 '是'，咱收工" | 如果那个"是"出现在含糊的重述或"听起来不错"之后，这"是"是空的。重写得具体再确认。 |

## 红旗

- 一条消息里问三个或更多问题：那叫批处理，不是访谈
- 提问不带你的假设：那叫问卷，不是承诺
- 把"随你"当最终答案
- 在用户明确确认你的重述前就开规格、规划、任务列表
- 拿到明确确认后立即调用工具或开始下游工作而不是停轮
- 问题被框成"最佳实践是？"而不是"你真正想要的是？"
- 用户给出迎合式回答（"可扩展"、"清晰"、"现代"），你不深挖就认
- 问了三轮以上置信度明显不上去：问错了，回头重新框
- 置信度低于 ~70% 但没附理由：用户没法帮你填空
- 在用户确认之前就把意图文档存了（文档本身就是用户没给的"是"）
- 重述时漏掉"不在范围"这一行（隐性分歧占错配的一半）

## 验证

用完 interview-me 后：

- [ ] 第一轮就给出了带置信度数字的明确假设
- [ ] 每个 <70% 的置信度都附一行"还缺什么"理由
- [ ] 问题一次一个问，每个都带上 Agent 的猜测
- [ ] 用户给出迎合式 / 惯例式答法时，至少跑过一句 "如果你不需要向任何人交代，你真正想要的是？"
- [ ] 把具体重述（目标 / 用户 / 为什么是现在 / 成功 / 约束 / 不在范围）写回了用户
- [ ] 用户以明确 "是" 确认了重述（不是"随你"、不是"听起来不错"、不是沉默）
- [ ] 停止点时，Agent 能预测接下来三个问题的反应
- [ ] 拿到明确确认后立即停轮，没有调用工具或启动下游工作
- [ ] 给下游 Skill（`idea-refine`、`spec-driven-development`）的任何接力都是围绕已确认的意图，而不是最初那个欠规格的请求
