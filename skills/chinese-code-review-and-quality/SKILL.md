# Code Review and Quality

## 概述

带质量门槛的多维度代码评审。每个改动在合并前都要被评审 ， 没有例外。评审覆盖五维度：正确性、可读性、架构、安全、性能。

**通过标准：** 当一个改动确定能提升整体代码健康时就放它过，即便它不完美。完美的代码不存在 ， 目标是持续改进。不要因为改动"不是我会写的样子"就拦下。如果它改善了代码库并遵守项目约定，就通过。

## 何时使用

- 合并任何 PR 或改动前
- 一个特性实现完成后
- 当另一个 Agent 或模型产出了代码需要你评估
- 正在重构既有代码
- 任何 bug 修复后（评审修复与回归测试）

## 五维度评审

每次评审都按这些维度评估：

### 1. 正确性

代码做出了它声称要做的事吗？

- 是否匹配规格或任务要求？
- 边界情况是否处理（null、空、边界值）？
- 错误路径是否处理（不仅是快乐路径）？
- 是否通过所有测试？测试是否真的测对了东西？
- 是否有差一错误、竞争条件或状态不一致？

### 2. 可读性与简洁

另一位工程师（或 Agent）能否不靠作者解释就读懂这段代码？

- 命名是否清晰、与项目约定一致？（不要在没有上下文的情况下用 `temp`、`data`、`result`）
- 控制流是否直接（避免嵌套三元、深度回调）？
- 代码组织是否合理（相关代码聚拢、模块边界清晰）？
- 是否有"取巧"该被简化？
- **能不能用更少行做？**（1000 行能 100 行写完是失败）
- **抽象挣回了它们的复杂度吗？**（不在第三个用例出现前通用化）
- 注释能帮澄清非显然的意图吗？（但不要注释显而易见的代码）
- 有没有死代码残骸：没用的变量（`_unused`）、向后兼容的垫片、`// removed` 注释？
- **新的条件是否被硬挂到不相关的流程？** 那是设计臭味，不是小问题 ， 把逻辑推进它自己的辅助、状态或策略，而不是拧进已有路径。
- **同样形状的重复条件出现了吗？** 它们标志着模型或调度器缺失。"临时"分支往往是永久债。

### 3. 架构

这个改动契合系统的设计吗？

- 是遵循已有模式，还是引入了新模式？若是新的，是否合理？
- 是否保持了清晰的模块边界？
- 是否有重复代码值得共享？
- 依赖方向是否正确（没有循环依赖）？
- 抽象层级是否合适（既不过度设计，也不太紧耦合）？
- **这次重构是在减少复杂度、还是只是把它搬到别处？** 数数读者要 hold 住多少概念才能跟上改动。如果"更整洁"的版本让这个数字不变，它就不是更整洁 ， 偏好那种能让整段分支、模式或层级消失的重构，而不是把同样的逻辑重新集中起来。宁愿删掉一个抽象，也不愿去打磨它。
- **特性专属逻辑是否漏进了共享 / 通用模块？** 把逻辑放在它所属的那层，复用已有的权威辅助而非近似的重复，不要把架构漂移正常化。
- **类型边界是否显式？** 质疑无端的 `any`/`unknown`/可选/强制类型转换，以及把不清晰的不变量偷偷兜底的默认 ， 把边界显式化常常让周围的控制流更简单。

### 4. 安全

详细安全指南见 `security-and-hardening`。改动是否引入了漏洞？

- 用户输入是否被校验、消毒？
- 密钥是否脱离了代码、日志、版本控制？
- 认证 / 授权检查是否在需要的地方出现？
- SQL 查询是否参数化（没有字符串拼接）？
- 输出是否编码以防 XSS？
- 依赖来源是否可信、无已知漏洞？
- 来自外部源（API、日志、用户内容、配置文件）的数据是否被当作不可信？
- 外部数据流在用于逻辑或渲染前是否被在系统边界做了校验？

### 5. 性能

详细 profiling 与优化见 `performance-optimization`。改动是否引入了性能问题？

- 有 N+1 查询模式吗？
- 有无界循环或未加约束的数据获取？
- 有该异步却同步的操作？
- UI 组件中有不必要的重渲染？
- 列表接口有缺分页的吗？
- 在热路径里有创建大对象？

## 结构性的修法

当你标出一个结构性问题，给出建议怎么改 ， 而不只是问题。只说"这很复杂"会让作者瞎猜。试试有名字的重构：

- **用 typed model 或显式调度器**替换一连串条件分支。
- **把重复分支合并**成一条更清晰的流。
- **把编排和业务逻辑分开**，让两边各自独立可读。
- **把特性专属逻辑**从共享模块搬进拥有这个概念的包。
- **复用权威辅助**，而不是现场写一个近似版本。
- **把类型边界显式化**，让下游分支自然消失。
- **删掉只过场的 wrapper**，只增间接不清 API。
- **抽一个 helper，或把大文件拆成专注的模块。**

优先选择"删掉可动的部分"而非"把同样的复杂度摊薄到各处"。

## 改动体量

小而聚焦的改动更易审、更快合并、更安全部署。目标尺寸：

```
~100 行变更   → 好。一次坐下来能看完。
~300 行变更   → 可以接受，前提是一个逻辑上的改动。
~1000 行变更  → 太大。拆。
```

**看文件大小，不只看 diff 大小。** 小 diff 也能把一个文件推过健康边界 ， 单文件 *总共* 约 1000 行（与上面的"~1000 *改* 行"门槛区分开）是常见的审查信号，不是硬上限。当改动实质性变大了本就大的文件，先问要不要先抽 helper、子组件或模块，**先拆再加**。

**"一项改动"算哪个：** 一项自包含的修改做一件事，带相关测试，提交后系统仍能工作。一个特性的一段 ， 不是整个特性。

**改动太大时的拆分策略：**

| 策略 | 怎么用 | 何时 |
|----------|-----|------|
| **栈式** | 提一条小改动，基于它做下一条 | 顺序依赖 |
| **按文件分组** | 对不同评审者感兴趣的群分开提 | 横切关注点 |
| **横向** | 先建共享代码 / stub，再去消费方 | 分层架构 |
| **纵向** | 把特性切成更小的全栈片 | 特性工作 |

**大改动何时可以接受：** 整个文件删除、由工具自动化的重构，评审者只需核对意图、不必逐行看时。

**把重构与功能分开。** 重构 + 加新行为是两件事 ， 分别提。小清理（重命名变量）可以视评审者偏好并入功能提交。

## 改动描述

每个改动都要有一份能独立存在的描述，在版本控制历史里站得住。

**第一行：** 简短、祈使句、能独立。"Delete the FizzBuzz RPC" 而不是 "Deleting the FizzBuzz RPC"。要信息足够，让搜历史的人能不看 diff 就理解这次改动。

**主体：** 改了什么、为什么。包括代码本身看不到的上下文、决策、推理。链接 bug 编号、benchmark 结果或设计文档。承认方法的不足。

**反模式：** "Fix bug"、"Fix build"、"Add patch"、"Moving code from A to B"、"Phase 1"、"Add convenience functions"。

## 评审流程

### 步骤 1：理解上下文

看代码前，先弄清意图：

```
- 这次改动想达成什么？
- 它实现了哪份规格或任务？
- 期望的行为变化是什么？
```

### 步骤 2：先评测试

测试揭示意图与覆盖：

```
- 这次改动有没有测试？
- 测试是测行为（而非实现细节）吗？
- 边界情况有覆盖吗？
- 测试的命名是否描述性？
- 若代码改了，这些测试还能抓住回归吗？
```

不要靠读，最后一个问题靠实验来回答：把这次改动加的某条件反转（去掉一个取反、把 `&&` 换成 `||`），跑一遍套件，再从一个备份恢复文件。一个仍然绿色的变异就是一条发现：说出缺的那条测试。整个项目级的变异分数见 `constraint-driven-development`。

### 步骤 3：评审实现

带着五维度通读代码：

```
对每个改动文件：
1. 正确性：这段代码做了测试说它该做的吗？
2. 可读性：不靠帮助我能读懂吗？
3. 架构：契合系统吗？
4. 安全：有什么漏洞吗？
5. 性能：有什么瓶颈吗？
```

### 步骤 4：把发现分类

每条评论都标严重级，让作者知道哪些是必须的哪些是可选：

| 前缀 | 含义 | 作者动作 |
|--------|---------|---------------|
| *（无前缀）* | 必改 | 必须在合并前处理 |
| **Critical:** | 阻塞合并 | 安全漏洞、数据丢失、功能损坏 |
| **Nit:** | 小且可选 | 作者可忽略 ， 格式、风格偏好 |
| **Optional:** / **Consider:** | 建议 | 值得考虑但不是必须 |
| **FYI** | 仅供信息 | 无需动作 ， 给将来留个上下文 |

这能防止作者把所有反馈都当强制，在可选建议上浪费时间。

**先讲重要的。** 按把控度排序发现：先正确性与安全，然后结构性回归与被遗漏的简化，再其它。不要把真实问题埋在琐碎 nit 下面 ， 几条高确信度的评论强过一份长清单。如果你有一个结构性问题加 10 条 nit，那个结构性问题*本身就是*这次评审的主线。

### 步骤 5：核查验证故事

看一眼作者的"验证经过"：

```
- 跑了哪些测试？
- 构建通过了吗？
- 做过手工测试吗？
- UI 改动有截图吗？
- 有没有 before/after 对比？
```

## 多模型评审模式

不同模型用于不同评审视角：

```
模型 A 写代码
    │
    ▼
模型 B 评正确性与架构
    │
    ▼
模型 A 处理反馈
    │
    ▼
人类拍板
```

这能抓到单个模型会漏的问题 ， 不同模型有不同的盲点。

**评审 Agent 的示例 prompt：**
```
从正确性、安全、对项目约定的遵守三方面评审这次代码改动。
规格说 [X]。改动应该 [Y]。
把问题标为 Critical、Required、Optional 或 Nit。
```

## 死代码卫生

每次重构或实现改动后，查一下孤儿代码：

1. 找出已经不可达或不用的代码
2. 显式列出
3. **删之前先问：** "应不应该把这些现在不用的元素移除：[列表]？"

不要把死代码留着 ， 它会让未来的读者和 Agent 困惑。但也不要默默删东西。看不准就问。

```
已识别的死代码：
- src/utils/date.ts 里的 formatLegacyDate() ， 已被 formatDate() 取代
- src/components/ 里的 OldTaskCard 组件 ， 已被 TaskCard 取代
- src/config.ts 里的 LEGACY_API_URL 常量 ， 已无任何引用
→ 这些能安全删除吗？
```

## 评审节奏

评审慢会卡整个团队。上下文切换的成本比让大家等待的成本低。

- **一个工作日内响应** ， 这是上限，不是目标
- **理想节奏：** 评审请求一进来就响应，除非你正在深度编码。典型改动应能在同一天内走完多轮
- **优先快速个人回复**而非快速最终批准。快速反馈减少挫败感，即便还需多轮
- **大改动：** 请作者拆，而不是自己评审一个超大变更集

## 处理分歧

评审争执出现时按这个层级：

1. **技术事实与数据**压过意见与偏好
2. **风格指南**对风格问题是绝对权威
3. **软件设计**必须按工程原则评判，而非个人偏好
4. **代码库一致性**在不降低整体健康的前提下可以接受

**不接受"我等会再清理"。** 经验显示延后清理几乎从不发生。除非紧急，要求提交前就清。如果一次改动无法处理周边问题，要求登记一个自接 bug。

## 评审中的诚实

评审代码 ， 不论是你写的、另一个 Agent 写的、还是人写的：

- **不要橡皮图章。** 没证据的 "LGTM" 对谁都没帮助。
- **不要软化真实问题。** 在"这只是个小顾虑"时其实是命中生产的 bug，那是不诚实。
- **能量化就量化问题。** "这条 N+1 查询每条记录加 ~50ms" 比 "这可能慢" 好。
- **方案有明显问题就 push back。** 逢迎是评审的失效模式。实现有问题，直接说、提替代。
- **接受被否决时得体。** 如果作者掌握完整上下文并不同意，尊重他的判断。评论代码，不要评论人 ， 把对人的批评重新框成对代码的关注。

## 依赖纪律

代码评审的一部分是依赖评审：

**加任何依赖前：**
1. 现有栈能解决这个吗？（往往可以）
2. 这个依赖多大？（看 bundle 影响）
3. 它被积极维护吗？（看最近提交、公开 issue）
4. 有没有已知漏洞？（`npm audit`）
5. 许可证是什么？必须与项目兼容。

**规则：** 优先用标准库和已有工具而非加新依赖。每个依赖都是一份负债。

**升级既有依赖**和别的代码改动一样，要按规矩走。最冒险的升级是那种批量合入、起个"bump deps"的：

1. **读 changelog，不光看版本号。** Semver 是维护者承诺的、可能没守住的东西 ， 一个 "patch" 可能带行为变化。主要版本升级要读迁移说明，看哪里会破。
2. **一次一个依赖。** 一个个升级、合入（或分小组）。一次批量升级挂掉后，你不知道是哪个包挂的；单包改动让原因明显、回滚干净。
3. **让测试说话。** 升级是否成功，由 *升级前* 和 *升级后* 的绿色套件说了算，不看"它装上了"。如果对该依赖行为的覆盖太薄，那才是真发现 ， 先补测试。
4. **看传递图。** 大多数安装的包都是没谁直接选的。审 lockfile diff，不光看 `package.json`；一次直接升级可以拉进几十处间接变化。
5. **保持 lockfile 诚实。** 提交它、审它的 diff，永远不要手工编辑。lockfile 才是真正钉住上线内容的东西。

对 `npm audit` 发现与供应链风险（typosquat、被攻陷维护者）的分流，跟着 `security-and-hardening` Skill ， 这节讲的是升级**流程**，那一节讲的是安全裁定。

```markdown
## Review: [PR/Change 标题]

### Context
- [ ] 我理解了这次改动做什么、为什么

### Correctness
- [ ] 改动匹配规格 / 任务要求
- [ ] 边界情况已处理
- [ ] 错误路径已处理
- [ ] 测试充分覆盖改动

### Readability
- [ ] 命名清晰一致
- [ ] 逻辑直接
- [ ] 没有不必要的复杂度

### Architecture
- [ ] 遵循已有模式
- [ ] 没有不必要的耦合或依赖
- [ ] 抽象层级合适
- [ ] 重构减少复杂度而非搬运
- [ ] 共享模块没有特性逻辑；文件保持在健康大小

### Security
- [ ] 没有密钥进代码
- [ ] 输入在边界已校验
- [ ] 没有注入漏洞
- [ ] auth 检查到位
- [ ] 外部数据源被当作不可信

### Performance
- [ ] 没有 N+1 模式
- [ ] 没有无界操作
- [ ] 列表接口有分页

### Verification
- [ ] 测试通过
- [ ] 构建成功
- [ ] 做过手工验证（如适用）

### Verdict
- [ ] **Approve** ， 准备合并
- [ ] **Request changes** ， 必须处理
```

## 常见借口

| Rationalization | Reality |
|---|---|
| "能跑就够了" | 能跑但难读、不安全、或架构错的代码，制造不断叠加的债。 |
| "我自己写的，我自己知道它对" | 作者对自己假设是盲的。每次改动都受益于另一双眼睛。 |
| "我们等会再清理" | "等会" 从不来。评审就是质量闸 ， 用它。要求合并前清理，不是之后。 |
| "AI 写的代码大概没问题" | AI 代码需要更多而不是更少的检视。它有自信且貌似有理，即使错了。 |
| "测试通过就行" | 测试必要但不充分。它们抓不到架构问题、安全问题、可读性问题。 |
| "这个重构让它更整洁了" | 搬动复杂度不是减少。如果读者仍要 hold 同样数量的概念，结构没改善 ， 去找那种让分支消失的版本。 |
| "只是给这个文件加了一点点" | 小 diff 也能把文件推过健康大小、并把分支硬拧进不相关流程。看结果结构，不是 diff 大小。 |
| "只是 version bump 而已" | 版本 bump 是一种"你没写过的行为变更"。读 changelog；semver 不保证不破。 |
| "我把所有升级塞一条 PR 省事" | 一次批量升级挂了，你就丢了是哪个包挂的。一个依赖一个改动让原因和回滚都干净。 |

## 红旗

- 没有任何评审就合的 PR
- 只测测试是否通过、忽略其他维度的评审
- 没真正评审过的 "LGTM"
- 安全敏感的改动没经过安全评审
- "太大审不动"的 PR（要拆）
- bug 修复 PR 没带回归测试
- 评审评论无严重级标签 ， 作者分不清必做与可选
- 接受 "我等会修" ， 那永远不会发生
- 一次把代码搬来搬去却不减少读者 hold 的概念数
- 改动让本已过大的文件更大而没拆
- 新条件散在不相关的代码路径里（缺抽象）
- 现场写一个近似 duplicate 的 helper，或把特性逻辑放在共享模块
- "bump dependencies" 批量 PR 没看 changelog、没做单包隔离
- lockfile 改动被手工编辑、没提交、或没看 diff 就合并
